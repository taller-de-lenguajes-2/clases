Arquitectura limpia

Propuesta por Robert C. Martin: mantener el código desacoplado y que resista los cambios de tecnología.

CírculoQué hayEn la clínica

Casos de usoLo que hace la aplicación«sacar un turno»
InfraestructuraBase, web, mail…controladores, repositorios
Las dependencias apuntan hacia adentro: el centro no conoce a SQLite ni a Razor.

El dominio

Es de qué trata un sistema y cómo funcionan las cosas en ese mundo, sin importar la tecnología.

Entidades

Los objetos principales: Libro, Socio, Préstamo.

Objetos de valor

Datos con significado pero sin identidad: un Monto, una FechaDeVencimiento.

Reglas de negocio

Cómo se comportan: «un socio no tiene más de 5 libros a la vez».

Casos de uso

Coordinan entidades: «registrar un préstamo».

Lógica (o reglas) de negocio

Las reglas, decisiones y procesos que dicen cómo funciona el dominio: qué se permite, qué no, y qué pasa en cada caso.

En un restaurante: un pedido no se puede cerrar sin al menos un plato confirmado, y el total incluye los impuestos que correspondan.

Lo que no es lógica de negocio

el teclado y la pantalla la sintaxis SQL las librerías de terceros el motor que arma el HTML si la respuesta va en JSON o XML

Eso son detalles técnicos: pueden cambiar sin que cambien las reglas.

Ejercicio: una biblioteca pública

El sistema registra libros, socios y préstamos. ¿Qué reglas tiene? Primero la pregunta, después la regla.

PreguntaRegla
¿Cuántos libros puede tener un socio a la vez?Hasta 5 libros al mismo tiempo.
¿Y si el libro ya lo tiene otro socio?Se avisa que está prestado y no se presta hasta que vuelva.
¿Cuánto tiempo puede tenerlo?14 días desde que lo retira.
¿Y si lo devuelve tarde?Una multa por día de atraso.
¿Y si tiene multas sin pagar?No puede sacar otro libro.
¿Hay libros que no se pueden llevar?Los de referencia solo se consultan en la sala.
Eso es la lógica de negocio. Cómo se guarda, cómo se muestra o qué base se usa son detalles técnicos que pueden cambiar sin tocar estas reglas.

Y en la clínica…

  • No hay dos pacientes con el mismo DNI
  • Un médico no atiende dos turnos a la misma hora
  • No se dan turnos en fechas que ya pasaron
  • Un paciente con turnos no se puede borrar

¿Dónde va cada una?

ReglaLa controla
DNI únicola base (UNIQUE) y la Recepcion del tema 09
Paciente con turnosla base (FOREIGN KEY)
Fechas pasadas, horariosel código del dominio

Algunas reglas las garantiza la base; otras son código. Ninguna va en la vista.

Entidad, regla y modelo

Entidad

Un concepto central del negocio, que persiste en el tiempo y tiene identidad.

Un Libro con título, autor e ISBN.

Regla de negocio

Lo que está permitido y lo que no. Gobierna a las entidades.

Un préstamo vence a los 14 días.

Modelo

Una estructura para transportar o adaptar datos hacia o desde afuera. Sin lógica.

Lo que viaja por la API o llega a una vista.

public class Prestamo                       // una entidad con su regla adentro
{
    public DateTime Retiro { get; set; }
    public DateTime Vencimiento => Retiro.AddDays(14);
    public bool EstaVencido(DateTime hoy) => hoy > Vencimiento;
}

Dos tipos de reglas

Afuera · no es regla de negocio

¿Eligió un socio? ¿El Id es un número? La forma del dato se controla antes de llamar al caso de uso.

Reglas de la aplicación · RegistrarPrestamo

El flujo del sistema: qué buscar, en qué orden, qué hacer si falla. Consigue los datos y le pregunta a la entidad.

Socio socio = socios.Obtener(socioId);
int activos = prestamos.ActivosDelSocio(socioId);   // ← la base
if (!socio.PuedeLlevarOtro(activos))                // ← le pregunta
    return Resultado.Error("Ya tiene 5 libros");
if (prestamos.EstaPrestado(libroId))
    return Resultado.Error("El libro está prestado");
prestamos.Guardar(new Prestamo { Retiro = DateTime.Today, … });

Reglas del negocio · Prestamo y Socio

Existirían aunque la biblioteca funcionara con fichas de papel. Deciden con los datos que tienen o que les pasan.

public DateTime Vencimiento => Retiro.AddDays(14);            // Prestamo
public bool PuedeLlevarOtro(int activos) => activos < 5;    // Socio
¿Existiría con fichas de papel? → la entidad. ¿Es parte de cómo funciona el sistema? → el caso de uso. La entidad decide; el caso de uso busca los datos y le pregunta.

Son los círculos del slide 3 vistos como capas: cada una depende de la de abajo. Robert C. Martin, Clean Architecture (2017), cap. 20: Critical Business Rules y Application-specific Business Rules.

Un modelo para cada tarea

Pueden tener los mismos datos que la entidad, pero en una versión plana y sin lógica, pensada para una tarea.

NombreParaEjemplo
DTO (Data Transfer Object)Enviar datos por una APILibroDTO: lo que devuelve GET /api/libros/7
ViewModelMostrar o cargar datos en una vistaLibroViewModel: fecha formateada, etiquetas
Registro (record)Representar cómo se guarda en la baseLibroRecord: una fila de la tabla
Hoy: los ViewModels, el modelo hecho a medida de una vista.

¿Qué es un ViewModel?

El objeto que se le pasa a una vista, con solo los datos que esa vista necesita, listos para mostrar.

  • A veces un modelo trae de más para la vista
  • A veces no alcanza: la vista necesita datos de dos modelos, o cosas que ningún modelo tiene

Model vs ViewModel

Model (entidad)ViewModel
RepresentaLos datos reales del dominio o de la baseUna pantalla concreta
Está cerca deEl núcleo del sistemaLa interfaz de usuario
Cuántos hayUno por concepto: TurnoLos que haga falta: TurnoListadoViewModel, TurnoCrearViewModel…
TieneIdentidad, relaciones, reglasTextos formateados, listas para desplegables, etiquetas
Si cambia la pantallaNo cambiaCambia

En las vistas de los temas 10 y 11 usábamos directamente las entidades (@model Paciente). Para pantallas simples alcanza; cuando la pantalla pide algo distinto del modelo, va un ViewModel.

Escenario 1: simplificar un modelo

El modelo: Turno

public class Turno
{
    public int Id { get; set; }
    public DateTime Fecha { get; set; }
    public string? Observaciones { get; set; }
    public Paciente Paciente { get; set; } = new();
    public Medico Medico { get; set; } = new();
}

Para una fila del listado sobran el DNI, el teléfono, el Id del médico… y falta el texto armado.

El ViewModel: una fila del listado

public class TurnoListadoViewModel
{
    public string Dia { get; }       // "mar 20/10"
    public string Hora { get; }      // "09:00"
    public string Paciente { get; }
    public string Medico { get; }    // "Inés Molina (Cardiología)"

    public TurnoListadoViewModel(Turno turno)
    {
        Dia = turno.Fecha.ToString("ddd dd/MM");
        Hora = turno.Fecha.ToString("HH:mm");
        Paciente = turno.Paciente.Nombre;
        Medico = $"{turno.Medico.Nombre} ({turno.Medico.Especialidad})";
    }
}

Escenario 2: dos modelos, una vista

public class PacienteDetalleViewModel
{
    public string Nombre { get; }
    public string DNI { get; }
    public string Telefono { get; }
    public List<TurnoListadoViewModel> ProximosTurnos { get; }
    public int TurnosAnteriores { get; }

    public PacienteDetalleViewModel(Paciente paciente, List<Turno> turnos)
    {
        Nombre = paciente.Nombre;
        DNI = paciente.DNI ?? "sin DNI";
        Telefono = paciente.Telefono ?? "sin teléfono";
        ProximosTurnos = turnos.Where(t => t.Fecha >= DateTime.Now)
                               .Select(t => new TurnoListadoViewModel(t))
                               .ToList();
        TurnosAnteriores = turnos.Count(t => t.Fecha < DateTime.Now);
    }
}

Puntos importantes

  1. Solo lo que usa la vista. Si una propiedad no se muestra ni se carga, no va.
  2. Un ViewModel por pantalla (o por formulario), con un nombre que lo diga: TurnoCrearViewModel.
  3. Sin lógica de negocio. Puede formatear ("ddd dd/MM"), pero las reglas viven en el dominio.
  4. Etiquetas con [Display], que usan los tag helpers asp-for.
  5. Validación con anotaciones ([Required], [StringLength]…) en el ViewModel del formulario: el tema 13.

Por convención, van en una carpeta ViewModels/, al lado de Models/.

Capa anticorrupción

Un adaptador entre dos partes que no hablan el mismo idioma, para que una no contamine a la otra.

Viene del Diseño Guiado por el Dominio (DDD). Microsoft la define como una fachada o capa de adaptación entre subsistemas que no comparten la misma semántica.

¿Para qué sirve?

Lógica de negocio

No se preocupa por cómo funciona la base ni por cómo se ve la página.

Front end

Las personas reciben datos útiles para ellas, no la estructura interna de las tablas.

Web API

Devuelve DTOs pensados para quien la consume, no las entidades tal cual.

Seguridad

Pasan solo los datos que la otra parte necesita: ni el hash de la contraseña, ni campos de más.

En la clínica ya hay dos: el repositorio (tema 09) entre la base y el dominio, y los ViewModels entre el dominio y las vistas.
