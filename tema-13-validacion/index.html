¿Por qué validar?

En el tema 11 el formulario guardaba lo que llegara. ¿Qué puede llegar?

  • Un paciente sin nombre, o con el nombre «a»
  • Un DNI 12.345.678, con puntos, o hola
  • Un turno para ayer, o a la hora en que el médico ya atiende a otro
  • Un request armado a mano, sin pasar por nuestro formulario
Regla de oro: nunca confiar en lo que llega del cliente. Puede ser un error de quien carga… o alguien probando qué pasa.

¿Dónde validar? En los dos lados

Front end · JavaScript

  • Avisa al instante, sin ir al servidor
  • Es por comodidad de quien carga
  • Se puede saltear: desactivar JavaScript, editar el HTML, mandar el request con otra herramienta

Back end · C#

  • Es la que protege los datos
  • No se puede saltear: todo pasa por el servidor
  • Puede consultar la base: «¿ese DNI ya existe?»
La del navegador es opcional y la del servidor es obligatoria. Y la base (NOT NULL, UNIQUE, FOREIGN KEY) es la última red.

¿Escribir todo dos veces?

En JavaScript…

if (!/^\d{7,8}$/.test(dni.value)) {
    error.textContent = "El DNI son 7 u 8 números";
    return false;
}

…y en C#

if (!Regex.IsMatch(modelo.DNI, @"^\d{7,8}$"))
{
    error = "El DNI son 7 u 8 números";
    return View(modelo);
}

Por cada campo, por cada formulario, en dos lenguajes. ¿Y cuando el DNI pase a tener 9 dígitos?

Cambiar en un lado y olvidarse del otro es cuestión de tiempo.

DRY: Don't Repeat Yourself

«Cada pieza de conocimiento debe tener una representación única, inequívoca y con autoridad dentro de un sistema.»

Andrew Hunt y David Thomas — The Pragmatic Programmer (1999), traducción libre

«Pieza de conocimiento» en sentido amplio:

  • datos guardados en una base
  • el código fuente
  • la documentación

Duplicar hace más difíciles los cambios, oscurece el código y abre la puerta a que las copias no coincidan.

La regla, una sola vez

ASP.NET MVC sigue DRY: la regla se declara una vez y la aplicación la refleja en los dos lados.

Atributos de validación

using System.ComponentModel.DataAnnotations;

public class PacienteCrearViewModel
{
    [Required(ErrorMessage = "El nombre es obligatorio.")]
    [StringLength(100, MinimumLength = 3,
        ErrorMessage = "El nombre tiene que tener entre {2} y {1} letras.")]
    public string Nombre { get; set; } = "";

    [RegularExpression(@"^\d{7,8}$",
        ErrorMessage = "El DNI son 7 u 8 números, sin puntos.")]
    public string? DNI { get; set; }

    [Display(Name = "Teléfono")]
    [Phone(ErrorMessage = "El teléfono no tiene un formato válido.")]
    public string? Telefono { get; set; }
}
  • Están en System.ComponentModel.DataAnnotations
  • Se aplican a propiedades, una o varias por propiedad
  • Van en el ViewModel del formulario (tema 12)
  • En el mensaje, {0} es el nombre del campo y {1}, {2}… los parámetros del atributo

Los atributos que vienen

AtributoValida que…Ejemplo
[Required]tenga valor: ni null ni texto vacíoel nombre del paciente
[StringLength(max)]el texto no pase de un largo (y opcional, un mínimo)observaciones hasta 200
[Range(min, max)]el número esté en un intervaloedad entre 0 y 120
[RegularExpression(patrón)]el texto respete un patrónDNI de 7 u 8 dígitos
[EmailAddress] · [Phone] · [Url]tenga forma de mail, teléfono o URLana@mail.com
[Compare("Otra")]sea igual a otra propiedad«repetir contraseña»
[ValidateNever]la propiedad no se validelas listas de un desplegable

Con <Nullable>enable, una propiedad string (sin ?) es obligatoria aunque no tenga [Required]. Y si en un campo int llega "abc", el binding ya agrega un error.

Un atributo propio

public class FechaFuturaAttribute : ValidationAttribute
{
    public FechaFuturaAttribute()
        : base("{0}: tiene que ser posterior a este momento.") { }

    public override bool IsValid(object? value)
    {
        // null lo resuelve [Required]
        return value is not DateTime fecha || fecha > DateTime.Now;
    }
}
  • Hereda de ValidationAttribute y sobrescribe IsValid (herencia y polimorfismo, tema 03)
  • El nombre termina en Attribute; al usarlo se escribe [FechaFutura]
  • Se escribe una vez y sirve para cualquier fecha: DRY
Fecha y hora: tiene que ser posterior a este momento.

Este corre solo en el servidor. Para que también valide en el navegador hay que escribirle la parte de JavaScript (IClientModelValidator).

En el servidor: ModelState

[HttpPost]
[ValidateAntiForgeryToken]
public IActionResult Crear(PacienteCrearViewModel modelo)
{
    if (!ModelState.IsValid)
    {
        return View(modelo);    // el mismo formulario, con lo que cargó y los errores
    }

    var paciente = new Paciente { Nombre = modelo.Nombre, … };
    int id = pacientes.Insertar(paciente);
    return RedirectToAction(nameof(Detalle), new { id });
}
  1. Llega el POST y se arma el ViewModel (binding)
  2. Corren todos los atributos
  3. Cada error queda en ModelState, con el nombre del campo
  4. La acción pregunta ModelState.IsValid
Sin ese if, los atributos no frenan nada: la acción sigue y guarda igual.

Reglas que necesitan la base

Un atributo mira un valor; no sabe si ese DNI ya está cargado ni si el médico está ocupado. Esas reglas se agregan a mano:

// PacientesController.Crear
if (!string.IsNullOrEmpty(modelo.DNI)
    && pacientes.ExisteDni(modelo.DNI))
{
    ModelState.AddModelError(nameof(modelo.DNI),
        "Ya hay un paciente con ese DNI.");
}

if (!ModelState.IsValid) return View(modelo);
// TurnosController.Crear
if (turnos.MedicoOcupado(medicoId, fecha))
{
    ModelState.AddModelError(nameof(modelo.Fecha),
        $"{medico.Nombre} ya tiene un turno a esa hora.");
}
Laura Sosa ya tiene un turno a esa hora.

AddModelError suma el error al campo: se muestra igual que los de los atributos. Con "" como nombre de campo, el error es del formulario entero.

Mostrar los errores

<form asp-action="Crear" method="post">
    <div asp-validation-summary="ModelOnly"></div>

    <label asp-for="DNI"></label>
    <input asp-for="DNI" />
    <span asp-validation-for="DNI"></span>
    …
</form>
Tag helperMuestra
asp-validation-forel error de un campo
asp-validation-summary="All"todos los errores, en una lista
asp-validation-summary="ModelOnly"solo los que no son de un campo

El campo con error recibe la clase input-validation-error y el mensaje, field-validation-error: el estilo lo pone nuestro CSS.

En el navegador

Lo que genera asp-for

<input type="text" id="DNI" name="DNI"
  data-val="true"
  data-val-regex="El DNI son 7 u 8 números, sin puntos."
  data-val-regex-pattern="^\d{7,8}$" />

<input type="text" id="Nombre" name="Nombre" maxlength="100"
  data-val="true"
  data-val-required="El nombre es obligatorio."
  data-val-length-min="3" data-val-length-max="100" … />

Las librerías que lo leen

@section Scripts {
    <partial name="_ValidationScriptsPartial" />
}
  • Carga jQuery, jQuery Validation y jQuery Validation Unobtrusive
  • La última traduce los data-val-* a reglas de jQuery Validation
  • Si hay errores, el formulario no se envía

La plantilla de Visual Studio trae el partial y las librerías en wwwroot/lib. En el ejemplo se cargan de un CDN.

El servidor tiene la última palabra

Algunas reglas no llegan al navegador:

ReglaEn el navegadorEn el servidor
[Required], [StringLength], [RegularExpression]✔✔
[Phone]✘ jQuery Validation no tiene esa regla✔
[FechaFutura] (nuestro)✘ no le escribimos la parte de JS✔
DNI repetido, médico ocupado✘ necesitan la base✔
Y si alguien manda el POST sin pasar por el formulario, ninguna corre en el navegador. Por eso ModelState.IsValid va siempre.

Para probarlo: desactivar JavaScript en el navegador, o mandar el POST desde un archivo .http.

QuéDóndeEjemplo

Integridad de los datosLa baseNOT NULL, UNIQUE, FOREIGN KEY
Comodidad de quien cargaEl navegador, generado de los atributosaviso antes de enviar

Una Web API también usa ModelState: con [ApiController], si no es válido responde 400 Bad Request solo, con la lista de errores en JSON.
