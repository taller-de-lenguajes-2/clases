¿Qué es ASP.NET?

ASP (Active Server Pages) es la tecnología de Microsoft para crear aplicaciones web: ejecuta código del lado del servidor para generar y servir contenido. Para crear Web APIs, ASP.NET Core ofrece dos caminos:

Basadas en controladores

Enfoque robusto y estructurado: clases controladoras que heredan de ControllerBase separan responsabilidades por recurso.

★ La que usamos en la materia — escala mejor y ordena el proyecto.

Minimal API

Enfoque simplificado: se declaran rutas y acciones directamente, con mínima configuración y sin controladores.

Útil para APIs chicas y prototipos.

Crear el proyecto

Todo desde la terminal, con el SDK de .NET:

  • dotnet --list-sdks — qué SDKs tengo instalados
  • dotnet new list — qué plantillas de proyecto existen
  • dotnet new webapi --use-controllers -o MiWebAPI — crea la Web API basada en controladores, en la carpeta MiWebAPI
  • cd MiWebAPI — entrar a la carpeta: los comandos dotnet buscan el proyecto en la carpeta actual
  • code . — abre el proyecto en VS Code
# ¿qué SDK tengo?
dotnet --list-sdks

# crear la Web API con controladores
dotnet new webapi --use-controllers -o MiWebAPI

# entrar a la carpeta y abrirla en VS Code
cd MiWebAPI
code .

# correrla (desde adentro de MiWebAPI)
dotnet run

El viaje de un request

Middleware

  • Es el mecanismo que permite procesar las solicitudes HTTP de manera modular: cada pieza hace una tarea y pasa el control a la siguiente
  • Se organizan en una cadena o “pipeline”: la solicitud los atraviesa en orden, y la respuesta vuelve por el mismo camino
  • Cada middleware puede procesar la solicitud, tomar decisiones o modificar la respuesta — incluso cortar el viaje (ej.: si no estás autenticado, nunca llegás al controlador)

Program.cs: armar la aplicación

// 1 · construir el builder
var builder = WebApplication.CreateBuilder(args);

// 2 · registrar servicios
builder.Services.AddControllers();

// 3 · construir la aplicación
var app = builder.Build();

// 4 · armar el pipeline de middlewares
app.UseHttpsRedirection();
app.UseAuthorization();
app.MapControllers();

// 5 · ejecutar
app.Run();
  • 1–2: el builder junta configuración y servicios que la app va a usar
  • 3: Build() construye el objeto aplicación
  • 4: cada Use… agrega un middleware al pipeline — el orden acá es el orden del viaje
  • 5: Run() pone el servidor a escuchar
MapControllers() es el que conecta el pipeline con nuestros controladores.

¿Qué es un controlador?

Es la clase que atiende las solicitudes HTTP: el punto de entrada de la API. Sus métodos públicos se llaman acciones — cuando llega una solicitud, el framework la enruta a una acción.

  • Se marcan con el atributo [ApiController]
  • Heredan de ControllerBase
  • Reciben el request y emiten la respuesta
ControllerBaseController
ParaWeb APIPáginas web
DevuelveJSONVistas (HTML)

Controller hereda de ControllerBase y agrega soporte de vistas — si tu controlador necesita vistas y API, derivá de Controller. Para API pura: ControllerBase.

Atributos en C#

  • Son clases que heredan de Attribute y funcionan como etiquetas sobre otros fragmentos de código
  • Asocian metadatos — información declarativa — a clases, métodos, propiedades…
  • Se escriben entre corchetes, antepuestos a lo que etiquetan
⚠ En alguna bibliografía en español aparecen como “decoradores” por mala traducción: en C# se llaman atributos.
[Atributo]
public class MiNuevaClase
{
    // elementos de la clase…
}

[Atributo]
public void MiMetodo()
{
    // código del método…
}

Ruteo: de la URL a la acción

El middleware de routing hace coincidir la URL entrante con un controlador y una acción. Dos formas de controlarlo:

Convencional

Una plantilla de ruta definida al inicio mapea las solicitudes:

"{controller}/{action}/{id?}"

{controller} → la clase · {action} → el método · {id?} → parámetro opcional

Por atributos ★

La ruta se define sobre el código mismo con atributos:

[ApiController]
[Route("[controller]")]

[ApiController] lo marca como controlador de API · [Route] define su ruta de acceso. Es la forma que usamos.

Un controlador, anotado

[ApiController]              // ① es un controlador
[Route("[controller]")]     // ② su ruta = su nombre
public class PronosticoDelClimaController
    : ControllerBase         // ③ herencia API
{
    [HttpGet]                // ④ verbo que atiende
    public IActionResult GetClimaHoy()
    {
        // código que devuelve el clima
        return Ok(clima);
    }
}

La acción queda publicada en:

GET https://localhost:5001/PronosticoDelClima
  • [Route("[controller]")] usa el nombre de la clase — sin el sufijo Controller, que por convención no impacta en la ruta
  • La acción responde a GET por su atributo [HttpGet]. El nombre del método no forma parte de la URL: /PronosticoDelClima/GetClimaHoy da 404
  • Para sumar un tramo a la ruta, se escribe en el atributo: [HttpGet("hoy")] → /PronosticoDelClima/hoy

Un atributo por verbo

Cada acción declara qué verbo atiende. El texto entre paréntesis es una plantilla de ruta que se suma a la del controlador.

AtributoPara quéRequest de ejemploDatos que traeResponde
[HttpGet]Leer una listaGET api/pacientes?pagina=2Filtros (query string)200 + lista
[HttpGet("{id}")]Leer unoGET api/pacientes/5El id (ruta)200 · 404
[HttpPost]CrearPOST api/pacientesEl paciente nuevo (body)201 + Location
[HttpPut("{id}")]Reemplazar enteroPUT api/pacientes/5Id (ruta) + paciente entero (body)204 · 404
[HttpPatch("{id}")]Cambiar una partePATCH api/pacientes/5Id (ruta) + lo que cambia (body)204 · 404
[HttpDelete("{id}")]BorrarDELETE api/pacientes/5El id (ruta)204 · 404
[Route("api/[controller]")] + [HttpGet("{id}")] = GET api/pacientes/5. Sin texto ([HttpGet]), la acción responde en la ruta del controlador tal cual.

Un controlador CRUD

[ApiController]
[Route("api/[controller]")]
public class PacientesController : ControllerBase
{
    [HttpGet]
    public IActionResult Listar() => Ok(pacientes);

    [HttpGet("{id:int}")]
    public IActionResult Obtener(int id)
    {
        var p = pacientes.Find(x => x.Id == id);
        return p is null ? NotFound() : Ok(p);
    }

    [HttpPost]
    public IActionResult Crear([FromBody] Paciente p)
    {
        pacientes.Add(p);
        return CreatedAtAction(nameof(Obtener), new { id = p.Id }, p);
    }

    [HttpDelete("{id:int}")]
    public IActionResult Borrar(int id) =>
        pacientes.RemoveAll(x => x.Id == id) > 0
            ? NoContent() : NotFound();
}

pacientes es una List<Paciente> en memoria. Qué pasa con cada request:

RequestResultado
GET api/pacientesListar() → 200
GET api/pacientes/5Obtener(5) → 200 o 404
GET api/pacientes/abc404: abc no es int, ninguna ruta coincide
POST api/pacientesCrear(p) con el JSON del body → 201
DELETE api/pacientes/5204; si se repite, 404
PATCH api/pacientes/5405: la ruta existe, el verbo no
CreatedAtAction agrega el header Location con la URL del nuevo paciente (…/api/Pacientes/7), armada a partir de Obtener.

Parámetros en la ruta

// obligatorio: el nombre entre llaves = el nombre del parámetro
[HttpGet("{id}")]
public IActionResult Obtener(int id)
// api/pacientes/5 → id = 5

// con restricción de tipo: si no cumple, la ruta no coincide
[HttpGet("{id:int}")]
// api/pacientes/abc → 404

// opcional (?) con valor por defecto
[HttpGet("pagina/{nro:int?}")]
public IActionResult Pagina(int nro = 1)
// api/pacientes/pagina → 1 · api/pacientes/pagina/4 → 4

// varios segmentos
[HttpGet("{pacienteId:int}/turnos/{turnoId:int}")]
public IActionResult Turno(int pacienteId, int turnoId)
// api/pacientes/5/turnos/12

// fechas: siempre en formato ISO (año-mes-día)
[HttpGet("turnos/{fecha:datetime}")]
public IActionResult TurnosDelDia(DateTime fecha)
// …/turnos/2026-11-22 ✓ · …/turnos/22-11-2026 → 404
RestricciónAcepta
{id:int}enteros: 5, -3
{activo:bool}true / false
{fecha:datetime}fechas: 2026-11-22
{codigo:guid}un Guid
{nombre:alpha}solo letras
{id:min(1)}enteros desde 1
{dni:length(8)}texto de 8 caracteres
{id:int:min(1)}se pueden encadenar
Con restricción, un valor inválido da 404: la ruta no coincide. Sin restricción, el request llega a la acción, falla la conversión y [ApiController] responde 400.

Parámetros por query string

// simples: se vinculan por nombre, sin importar el orden
[HttpGet("buscar")]
public IActionResult Buscar(string nombre, int edad)
// api/pacientes/buscar?edad=3&nombre=Carlos

// opcionales: valor por defecto o tipo nullable (?)
[HttpGet]
public IActionResult Listar(int pagina = 1, int tamanio = 20,
                           bool? activo = null)
// api/pacientes?pagina=2 → tamanio = 20, activo = null

// listas: se repite la clave
[HttpGet("por-ids")]
public IActionResult PorIds([FromQuery] int[] id)
// …/por-ids?id=1&id=4&id=9 → [1, 4, 9]

// otro nombre en la URL
public IActionResult Texto([FromQuery(Name = "q")] string texto)
// …?q=perez → texto = "perez"

// muchos filtros: una clase que los agrupa
public IActionResult Filtrar([FromQuery] FiltroPacientes filtro)
// …?obra=OSDE&edadMin=18 → filtro.Obra, filtro.EdadMin

Con Buscar(string nombre, int edad):

Query stringQué llega
?edad=3&nombre=Carlos"Carlos" y 3
?NOMBRE=Carlos&EDAD=3lo mismo: no distingue mayúsculas
?nombre=Carlosedad = 0: un int que falta toma su valor por defecto
?edad=3400: un string no nullable es obligatorio
?edad=tres&nombre=Carlos400: tres no es un int
¿Querés que un texto sea opcional? Declaralo string? nombre: si no viene, llega null.

¿De dónde vienen los datos?

Los atributos From… indican de qué parte del request se toma cada parámetro:

AtributoFuenteEjemplo en el requestEn la acción
[FromRoute]La rutaPUT /api/pacientes/5[FromRoute] int id
[FromQuery]El query stringGET /api/pacientes?pagina=2[FromQuery] int pagina
[FromHeader]Un headerX-Api-Key: abc123[FromHeader(Name = "X-Api-Key")] string apiKey
[FromBody]El body (JSON){ "nombre": "Ana" }[FromBody] Paciente paciente
[FromForm]Un formulario en el bodycampos de un <form>, archivos[FromForm] IFormFile foto
ASP.NET convierte el JSON del body directo en un objeto Paciente: la abstracción viaja por la red.

Si no ponés ningún From…

Con [ApiController], ASP.NET deduce la fuente de cada parámetro, en este orden:

  • ¿Su nombre está entre llaves en la plantilla? → ruta
  • ¿Es un tipo simple que no está en la plantilla? → query string
  • ¿Es una clase? → body
  • Los headers nunca se deducen: siempre [FromHeader]
La plantilla del atributo describe solo la ruta. El query string y el body no se declaran ahí: ASP.NET los busca solo.
[HttpPut("{id:int}")]
public IActionResult Reemplazar(
    int id,              // en la plantilla → ruta
    bool notificar,      // simple → query string
    Paciente paciente)  // clase → body

Atiende este request:

PUT /api/pacientes/5?notificar=true
Content-Type: application/json

{ "id": 5, "nombre": "Ana Paz" }

¿Y si notificar estuviera en la plantilla? Pasaría a ser parte de la ruta:

[HttpPut("{id:int}/{notificar:bool}")]   // PUT /api/pacientes/5/true

    [FromRoute]  int id,
    [FromQuery]  bool notificar,
    [FromHeader(Name = "X-Api-Key")]
                 string apiKey,
    [FromBody]   Paciente paciente)

    // id = 5 · notificar = true
    // apiKey = "abc123"
    // paciente.Nombre = "Ana Paz"
}

Ruta

En la línea inicial, visible en la URL. Dice qué recurso.

Query string

También en la URL. Opciones y filtros cortos; queda en historiales y logs.

Header

Fuera de la URL. Datos sobre el pedido: claves, tokens, formato.

Body

Fuera de la URL. Los datos grandes o con estructura: el objeto entero.

Devolver respuestas

IActionResult / ActionResult<T> representan el resultado de una acción y permiten devolver distintos tipos de respuesta según la situación:

[HttpGet]
public ActionResult<List<Producto>> Get()
{
    var productos = new List<Producto>();
    return Ok(productos);   // 200 + JSON
}

Documentar la API: OpenAPI

El problema: exponemos endpoints…

GET    /api/pacientes      → lista
POST   /api/pacientes      → crea
PUT    /api/pacientes/5    → actualiza
DELETE /api/pacientes/5    → elimina

…¿cómo los conoce quien consume la API sin leer nuestro código?

La solución: OpenAPI — un estándar abierto (ex Swagger, hoy de la OpenAPI Initiative junto a Google, Microsoft, IBM…) que describe la API en un documento JSON/YAML:

  • Qué endpoints existen, qué parámetros aceptan, qué devuelven
  • Herramientas de terceros lo leen automáticamente: generan clientes, SDKs y pruebas
  • Swagger UI lo convierte en una página para probar la API desde el navegador

Swagger UI en tres pasos

# 1 · instalar el paquete
dotnet add package Swashbuckle.AspNetCore
// 2 · registrar el servicio (Program.cs)
builder.Services.AddSwaggerGen();

// 3 · sumar los middlewares (solo en desarrollo)
if (app.Environment.IsDevelopment())
{
    app.UseSwagger();
    app.UseSwaggerUI();
}

Y para que la documentación se escriba sola, comentarios XML sobre las acciones:

/// <summary>
/// Obtiene los estudiantes activos
/// </summary>
/// <param name="id">ID del estudiante</param>
/// <response code="200">Operación exitosa</response>
/// <response code="404">No encontrado</response>
[HttpGet("{id}")]
public IActionResult Get(int id) { … }

Mismo código → documentación siempre actualizada + una herramienta para probar los endpoints en vivo.
