Primero la autenticación, después la autorización. Pero hay un problema: ¿cómo se acuerda el servidor de que ya iniciaste sesión?

HTTP no tiene estado

Cada request es independiente: el servidor no relaciona uno con el anterior. Para recordar algo entre requests hacen falta cookies.

¿Qué es una cookie?

Un dato chico, nombre=valor, que el servidor le pide al navegador que guarde, y que el navegador le devuelve en cada request a ese sitio.

Respuesta del servidor
Línea de estado
HTTP/1.1 302 Found
Headers
Set-Cookie: UltimoMedico=2; expires=…;
  path=/; samesite=lax; httponly
Cada request siguiente
Línea inicial
GET /Turnos/Crear HTTP/1.1
Headers
Host: localhost:5195
Cookie: UltimoMedico=2

La guarda el navegador, separada por sitio: un sitio no ve las cookies de otro. Se ven en las herramientas del navegador (Aplicación → Cookies).

Las opciones de una cookie

OpciónQué hace
Expires / MaxAgeHasta cuándo dura. Sin ninguna, se borra al cerrar el navegador (cookie de sesión del navegador)
HttpOnlyJavaScript no la puede leer: si alguien inyecta un script, no se la lleva
SecureSolo viaja por HTTPS
SameSiteSi se manda o no cuando el request viene desde otro sitio (Strict, Lax, None)
Path / DomainA qué rutas y dominios se manda

Tamaño máximo: unos 4 KB por cookie. Son para datos chicos.

Cookies en ASP.NET Core

// Escribir: viaja en la respuesta (Set-Cookie)
Response.Cookies.Append("UltimoMedico", medicoId.ToString(), new CookieOptions
{
    Expires = DateTimeOffset.Now.AddDays(30),
    HttpOnly = true,
    SameSite = SameSiteMode.Lax
});

// Leer: llegó en el request (Cookie). Si no está, null
string? valor = Request.Cookies["UltimoMedico"];
if (int.TryParse(valor, out int id))
    modelo.MedicoId = id;

// Borrar
Response.Cookies.Delete("UltimoMedico");

En el ejemplo: el formulario de turnos recuerda el último médico elegido, por 30 días.

  • Se escribe en Response, se lee de Request
  • Lo que se escribe recién se puede leer en el próximo request
  • Siempre es texto: hay que convertirlo y desconfiar (el usuario la puede cambiar)

Lo que no va en una cookie

// ✘ Nunca
Response.Cookies.Append("Usuario", "recepcion");
Response.Cookies.Append("Rol", "Recepcion");
Cookie: Usuario=recepcion; Rol=Admin   ← la editó a mano
  • La cookie está en la computadora del usuario: la puede leer y cambiar
  • Nada de contraseñas, roles ni datos personales
  • Sí: preferencias inofensivas (el último médico, el tema oscuro, el idioma)
Para saber quién es el usuario, la cookie lleva solo un identificador imposible de adivinar, y los datos quedan en el servidor. Eso es la sesión.

La sesión

Cada navegador tiene su Id; con el Id, el servidor encuentra sus datos. El usuario puede ver su Id, pero no los datos ni cambiar su rol.

Cookie vs sesión

Cookie propiaSesión
Dónde están los datosEn el navegadorEn el servidor (el navegador tiene solo el Id)
¿El usuario los puede cambiar?SíNo
Cuánto duraLo que diga Expires (días, meses)Hasta que pasa IdleTimeout sin actividad, o se reinicia la app
Tamaño~4 KBLo que aguante la memoria del servidor
ParaPreferencias: último médico, idiomaQuién inició sesión, su rol

La sesión usa una cookie, pero solo para el Id. Ninguna de las dos reemplaza a la base: lo que tiene que durar se guarda en la base.

Configurar la sesión en Program.cs

// 1 · Dónde se guardan los datos: en memoria
builder.Services.AddDistributedMemoryCache();

// 2 · El servicio de sesión y su cookie
builder.Services.AddSession(options =>
{
    options.IdleTimeout = TimeSpan.FromMinutes(20);
    options.Cookie.HttpOnly = true;
    options.Cookie.IsEssential = true;
});

builder.Services.AddControllersWithViews();
var app = builder.Build();

app.UseStaticFiles();
// 3 · El middleware, ANTES de los controladores
app.UseSession();

app.MapControllerRoute(…);
  • IdleTimeout: sin actividad ese tiempo, la sesión se pierde
  • HttpOnly: JavaScript no puede leer la cookie del Id
  • IsEssential: se manda aunque el usuario rechace las cookies opcionales
  • Si UseSession va después de MapControllerRoute, o falta, HttpContext.Session tira una excepción

Usar la sesión

// en un controlador: HttpContext.Session
HttpContext.Session.SetString("Nombre", "Marta");
HttpContext.Session.SetInt32("Intentos", 0);

string? nombre = HttpContext.Session.GetString("Nombre");
int? intentos = HttpContext.Session.GetInt32("Intentos");

HttpContext.Session.Remove("Intentos");   // una clave
HttpContext.Session.Clear();               // todas: cerrar sesión

Están en Microsoft.AspNetCore.Http (ya incluido en un proyecto web). Si la clave no existe, Get… devuelve null.

¿Y un objeto?

La sesión guarda texto, enteros o bytes. Para un objeto, se serializa a JSON (tema 05):

Session.SetString("Carrito",
    JsonSerializer.Serialize(carrito));

var carrito = JsonSerializer.Deserialize<Carrito>(
    Session.GetString("Carrito")!);

Mejor guardar poco: el Id o el nombre de usuario, no la lista de turnos.

Cada una con una responsabilidad (tema 09). El controlador no sabe cómo se guarda la sesión ni dónde están los usuarios.

El usuario y su repositorio

public class Usuario
{
    public string NombreUsuario { get; set; } = "";
    public string Nombre { get; set; } = "";
    public string Clave { get; set; } = "";
    public string Rol { get; set; } = "";   // "Recepcion" o "Admin"
}

public class UsuarioRepository
{
    private readonly List<Usuario> usuarios = [ … ];   // en memoria

    public Usuario? Obtener(string nombreUsuario) =>
        usuarios.FirstOrDefault(u => u.NombreUsuario == nombreUsuario);
}
⚠ Contraseñas en texto plano: solo para el ejemplo.

En un sistema real se guarda un hash de la contraseña (una huella que no se puede revertir) y se compara el hash de lo que escribió el usuario. .NET lo trae hecho: PasswordHasher<T>, o todo el sistema con ASP.NET Core Identity.

El servicio de autenticación

public class AutenticacionService(
    UsuarioRepository usuarios, IHttpContextAccessor httpContextAccessor)
{
    private ISession Sesion => httpContextAccessor.HttpContext!.Session;

    public bool Login(string nombreUsuario, string clave)
    {
        Usuario? usuario = usuarios.Obtener(nombreUsuario);
        if (usuario is null || usuario.Clave != clave) return false;

        Sesion.SetString("Usuario", usuario.NombreUsuario);
        Sesion.SetString("Nombre", usuario.Nombre);
        Sesion.SetString("Rol", usuario.Rol);
        return true;
    }

    public void Logout() => Sesion.Clear();
    public bool EstaAutenticado() => Sesion.GetString("Usuario") is not null;
    public bool TieneRol(string rol) => Sesion.GetString("Rol") == rol;
}
  • Un servicio no es un controlador: no tiene HttpContext a mano
  • IHttpContextAccessor le da el del request actual
// Program.cs
builder.Services.AddSingleton<UsuarioRepository>();
builder.Services.AddHttpContextAccessor();
builder.Services.AddScoped<AutenticacionService>();

Registrarlo así para que llegue por el constructor es el tema 14.

El controlador de login

[HttpPost]
[ValidateAntiForgeryToken]
public IActionResult Index(LoginViewModel modelo)
{
    if (!ModelState.IsValid) return View(modelo);

    if (!autenticacion.Login(modelo.NombreUsuario, modelo.Clave))
    {
        ModelState.AddModelError("", "Usuario o contraseña incorrectos.");
        return View(modelo);
    }

    if (Url.IsLocalUrl(modelo.ReturnUrl)) return Redirect(modelo.ReturnUrl);
    return RedirectToAction("Index", "Home");
}

[HttpPost]
[ValidateAntiForgeryToken]
public IActionResult Salir()
{
    autenticacion.Logout();
    return RedirectToAction("Index", "Home");
}
  • El error no dice si falló el usuario o la contraseña: no le da pistas a quien prueba
  • ReturnUrl: después de ingresar, vuelve a donde quería ir
  • Url.IsLocalUrl: solo a direcciones de nuestro sitio. Si no, un link trucho podría mandar al usuario a otro sitio después del login
  • Salir es POST: cambia el estado

Otra vez DRY (tema 13). La solución en ASP.NET: un filtro.

¿Qué es un filtro?

Código que corre antes o después de una acción, sin estar escrito dentro de ella.

Middleware (tema 06)Filtro
Cuándo correEn todo el pipeline, para cada requestAlrededor de las acciones de los controladores
SabeSolo del requestQué controlador y qué acción, sus parámetros
Se aplicaGlobalmente, en Program.csA una acción, a un controlador o a todos
EjemplosUseStaticFiles, UseSession[ValidateAntiForgeryToken], [RequiereLogin]

Ya veníamos usando uno: [ValidateAntiForgeryToken] es un filtro que corre antes de la acción.

Un filtro propio: [RequiereLogin]

public class RequiereLoginAttribute : ActionFilterAttribute
{
    public override void OnActionExecuting(ActionExecutingContext context)
    {
        var sesion = context.HttpContext.Session;
        if (sesion.GetString("Usuario") is null)
        {
            var pedido = context.HttpContext.Request;
            context.Result = new RedirectToActionResult("Index", "Login",
                new { returnUrl = pedido.Path + pedido.QueryString });
        }
    }
}
  • OnActionExecuting corre antes de la acción
  • Si pone un context.Result, la acción no se ejecuta: se responde eso
[RequiereLogin]       // todas las acciones
public class TurnosController : Controller
{ … }
GET /Turnos  →  302  /Login?returnUrl=%2FTurnos

Autorización: [RequiereRol]

public class RequiereRolAttribute(string rol)
    : ActionFilterAttribute
{
    public override void OnActionExecuting(
        ActionExecutingContext context)
    {
        if (context.HttpContext.Session
                .GetString("Rol") != rol)
        {
            context.Result =
                new ViewResult { ViewName = "SinPermiso" };
        }
    }
}
[RequiereLogin]
public class PacientesController : Controller
{
    public IActionResult Index(…)   { … }  // cualquiera logueado

    [HttpGet]
    [RequiereRol("Admin")]                  // solo administración
    public IActionResult Crear()         { … }
}

El atributo recibe un parámetro, como [StringLength(100)]. Con recepcion, /Pacientes/Crear muestra «Sin permiso»; con admin, el formulario.
