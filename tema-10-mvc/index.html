Un bar con un solo mozo

Supongamos un bar donde una sola persona hace todo.

Si se enferma el mozo, cierra el bar. Si cambia una receta, la tiene que aprender él. Si hay 30 mesas…

Repartir las responsabilidades

Mozo

Atiende al comensal, toma el pedido y lo lleva a la barra.

No sabe cocinar. No le hace falta.

Cocinero

Recibe el pedido y lo prepara con la carta de recetas y los recursos de la cocina.

No ve al comensal.

Cocina · recetas · materia prima

Lo que el cocinero usa. Cambiar de proveedor no cambia al mozo.

Cada uno hace una cosa y se comunica con los otros por algo acordado: el pedido.

Con el software pasa lo mismo: cada parte con su tarea, y lo justo de contacto entre ellas.

Dos medidas de un diseño

Acoplamiento

¿Cuánto depende una parte de las otras?

Entre módulos. Lo queremos bajo.

Cohesión

¿Cuánto tienen que ver entre sí las cosas de una misma parte?

Dentro de un módulo. La queremos alta.

En el bar: el mozo que cocina tiene baja cohesión (hace cosas que no tienen nada que ver) y todo el bar está acoplado a él.

¿Qué es el acoplamiento?

«La forma y el nivel de interdependencia entre módulos de software. Una medida de qué tan estrechamente conectadas están dos rutinas o módulos.»

ISO/IEC/IEEE 24765 — Systems and software engineering — Vocabulary (traducción libre)

En POO: hay acoplamiento cada vez que una clase usa un dato o un método de otra clase.

No se puede eliminar del todo (las clases tienen que colaborar), pero sí reducir: que cada clase sepa de las otras solo lo necesario.

¿Qué tiene de malo el acoplamiento alto?

Una clase conoce demasiado los detalles internos de otras, o depende directamente de ellas para muchas tareas.

Rígido

Un cambio en una clase obliga a cambiar muchas otras: efecto dominó.

Poco reutilizable

No se puede llevar una clase a otro lado sin arrastrar a todas las que usa.

Difícil de probar

Para probar una parte hay que armar todo lo demás.

Una clase con alta cohesión

public class Calculadora
{
    public int Sumar(int a, int b) => a + b;

    public int Restar(int a, int b) => a - b;

    public int Multiplicar(int a, int b) => a * b;

    public int Dividir(int dividendo, int divisor)
    {
        if (divisor == 0)
            throw new ArgumentException("No se puede dividir por cero.");
        return dividendo / divisor;
    }
}

La cohesión es cuánto se relacionan los métodos de una clase entre sí y con su responsabilidad.

  • Una sola responsabilidad: calcular
  • Todos los métodos son del mismo tema
  • ¿Un método GuardarEnArchivo() acá? Bajaría la cohesión

Caso: una tienda online

Un negocio de ropa vende por la web. Cada vez que alguien compra, el sistema tiene que:

  1. registrar el pedido,
  2. calcular el precio,
  3. generar la factura,
  4. y dejar todo listo para la entrega.
Parece lógico que una clase Pedido se encargue de todo. Al fin y al cabo, el pedido es el centro del proceso… ¿no?

Con el tiempo, Pedido crece: valida al cliente, revisa el stock, calcula impuestos, emite la factura, manda notificaciones…

Una clase muy acoplada

public class Pedido
{
    private Cliente cliente;
    private Producto producto;
    private Factura? factura;

    public Pedido(Cliente cliente, Producto producto)
    {
        this.cliente = cliente;
        this.producto = producto;
    }

    public void Procesar()
    {
        // valida al cliente, revisa el stock del producto,
        // calcula impuestos, avisa por mail…
    }

    public void GenerarFactura()
    {
        factura = new Factura(cliente, producto);
        factura.Emitir();
    }
}

A primera vista cumple. Pero controla demasiado:

  • Maneja la relación con el Cliente
  • Trabaja directamente con el Producto
  • Crea y emite la Factura
Si cambia la forma de facturar (por ejemplo, factura electrónica de AFIP/ARCA), hay que tocar Pedido.

Separar las responsabilidades

El pedido: solo datos

public class Pedido
{
    public Cliente Cliente { get; }
    public Producto Producto { get; }
    public bool Procesado { get; private set; }

    public Pedido(Cliente c, Producto p)
    {
        Cliente = c;
        Producto = p;
    }

    public void MarcarComoProcesado()
        => Procesado = true;
}
Cambiar la factura ahora toca una sola clase. Y ServicioDePedidos recibe con quién facturar por el constructor: es la idea del tema 14, inyección de dependencias.

Facturar

public class ServicioDeFacturacion
{
    public void GenerarFactura(Pedido pedido)
    {
        var factura = new Factura(
            pedido.Cliente, pedido.Producto);
        factura.Emitir();
    }
}

Coordinar

public class ServicioDePedidos(
    ServicioDeFacturacion facturacion)
{
    public void Procesar(Pedido pedido)
    {
        // validar, revisar stock…
        pedido.MarcarComoProcesado();
        facturacion.GenerarFactura(pedido);
    }
}

Bajo acoplamiento, alta cohesión

El bajo acoplamiento permite

  • Mantener mejor cada parte
  • Reutilizarla en otro lado
  • Cambiar una sin tener que cambiar muchas

La alta cohesión permite

  • Saber dónde está cada cosa
  • Clases chicas y fáciles de entender
  • Un motivo para cambiar por clase
Cuanto menos dependan entre sí las partes, mejor. Pero el desacoplamiento total es imposible: las partes tienen que colaborar.

Las partes de una web

Front end

Lo que corre en el navegador.

  • HTML, CSS y JavaScript
  • Pedidos asincrónicos (fetch)
  • Accesibilidad
  • Que funcione en todos los navegadores

Back end

Lo que corre en el servidor. Acá estamos nosotros: C#.

  • Reglas del negocio
  • Acceso a la base de datos
  • Seguridad
  • Escalar cuando hay muchos usuarios

En la Web API (tema 06) el servidor devolvía JSON y otro armaba la página. Con MVC, el servidor arma y devuelve el HTML.

Modelo · Vista · Controlador

Un patrón de arquitectura que divide una aplicación interactiva en tres partes.

Modelo

Los datos y las reglas del negocio. No sabe nada de pantallas.

Vista

Le muestra la información al usuario. Puede haber más de una para los mismos datos.

Controlador

Recibe lo que pide el usuario, usa el modelo y elige qué vista responde.

Program.cs: de Web API a MVC

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddScoped(_ => new PacienteRepository(cadenaConexion));
builder.Services.AddControllersWithViews();        // en la Web API: AddControllers()

var app = builder.Build();

app.UseStaticFiles();                              // sirve wwwroot: el CSS de las páginas

app.MapControllerRoute(                            // en la Web API: MapControllers()
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");

app.Run();

AddControllersWithViews

Controladores y el motor de vistas Razor.

MapControllerRoute

Una ruta convencional para todos, en vez de [Route] en cada controlador.

{controller=Home}/{action=Index}/{id?}

  • {id?}: el ? lo hace opcional
  • El sufijo Controller no va en la URL

El controlador

public class PacientesController(PacienteRepository repositorio)
    : Controller
{
    // GET /Pacientes
    public IActionResult Index()
    {
        List<Paciente> pacientes = repositorio.Listar();
        return View(pacientes);
    }

    // GET /Pacientes/Detalle/3
    public IActionResult Detalle(int id)
    {
        Paciente? paciente = repositorio.Obtener(id);
        if (paciente is null) return NotFound();

        return View(paciente);
    }
}
  • Hereda de Controller (la Web API usaba ControllerBase): suma View()
  • View(pacientes) le pasa el modelo a la vista
  • Sin [ApiController] ni [Route]: manda la ruta convencional
View() busca Views/Pacientes/Index.cshtml: carpeta del controlador, archivo de la acción.

La vista: HTML con C#
