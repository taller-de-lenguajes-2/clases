Formas de comunicación

Antes de hablar de APIs: ¿de cuántas maneras pueden comunicarse dos dispositivos?

Símplex →

Transmisión en un solo sentido: del que origina hacia el que recibe.

Ej.: una radio FM — la escuchás, no le contestás.

Semidúplex ⇄

Ambos sentidos, pero de manera alterna: uno habla por vez.

Ej.: un handy — “cambio y fuera”.

Dúplex ⇆

Ambos sentidos en simultáneo — la forma más eficiente.

Ej.: una llamada telefónica.

La web funciona sobre un ciclo de petición y respuesta: el cliente pide, el servidor contesta. Lo vemos enseguida.

¿Qué es una API?

API — Application Programming Interface — es un conjunto de reglas bien definidas que especifica formalmente la comunicación entre dos componentes de software.

  • El cliente accede al recurso solo a través de la API, nunca directo
  • Siempre estuvimos haciendo APIs: la interfaz pública de nuestras clases (Tema 01) es exactamente eso, un contrato de uso
¿Se acuerdan del Mozo del bar? El cliente nunca entra a la cocina: pide por el mozo. La API es el mozo del software.

Tipos de APIs según su acceso

Privadas (internas)

Conectan componentes dentro de una organización; no están disponibles para terceros.

Una app de redes sociales puede tener docenas: login, feed, mensajería…

Públicas

Dan acceso público a datos o servicios para que terceros los integren; gratuitas o pagas.

Un e-commerce integra la API de Stripe y no construye su pasarela de pagos.

De socios

Dos o más empresas comparten datos o funcionalidad para colaborar; requieren autenticación.

Solo las usan los socios autorizados.

¿Qué es REST?

  • Una API REST es una interfaz de comunicación entre sistemas que usa el protocolo HTTP para obtener datos o ejecutar operaciones sobre ellos, en formatos como JSON o XML
  • REpresentational State Transfer: transferencia de representaciones de estado — el servidor no manda “el objeto”, manda una representación de su estado
  • Una API es RESTful cuando cumple los estándares REST
REST no es una tecnología ni un producto: es un estilo de arquitectura con reglas claras — las vemos ahora.

Las restricciones de REST

Cliente-servidor

Las aplicaciones de cliente y servidor deben estar separadas — cada uno con su responsabilidad.

Sin estado

Cada petición es independiente y se resuelve completa: el servidor no recuerda peticiones anteriores.

Caché

Las respuestas pueden cachearse para evitar llamadas repetidas al servidor.

Interfaz uniforme

Cada recurso tiene un identificador único (URI): una ruta que lo nombra.

¿“Sin estado” les suena raro después del bar? El estado vive en el servidor o el cliente — pero cada petición trae todo lo necesario para resolverse sola.

Arquitectura cliente-servidor

Modelo de diseño donde las tareas se reparten entre servidores — proveedores de recursos o servicios — y clientes — los que los demandan.

  • El cliente realiza peticiones; el servidor responde
  • Separa la interfaz de usuario del almacenamiento de datos
  • En REST, la respuesta es una representación del estado del recurso solicitado

El protocolo HTTP

  • Hyper-Text Transfer Protocol: el idioma en que hablan cliente y servidor
  • Toda la comunicación gira en torno al ciclo solicitud-respuesta: el cliente pide algo (Request) y el servidor contesta si puede o no hacerlo (Response)
  • En HTTP/1.1 los mensajes son texto plano (se pueden leer); en HTTP/2 pasan a tramas binarias para optimizar la transmisión
Todo lo que sigue — verbos, URLs, códigos de estado — son las partes de ese mensaje. Aprender HTTP es aprender a leer y escribir estos mensajes.

Anatomía de una URL

La URI identifica el recurso; la URL además dice dónde está y cómo acceder:

Protocolo https://

Las reglas con que se hablan cliente y servidor. https es HTTP cifrado; http viaja en claro.

Subdominio www

Una subdivisión opcional que define el dueño del dominio: api., mail., campus.…

Dominio servicio.com

El nombre registrado del sitio; el DNS lo traduce a una IP. Termina en la extensión: .com, .ar, .com.ar.

Puerto :443

La “puerta” del servidor donde escucha el servicio. Si se omite, se usa la de siempre: 80 para http, 443 para https.

Ruta /productos/…

Identifica el recurso dentro del servidor, como carpetas. Es la parte que en REST nombra lo que pedimos.

Query string ?activos=1

Parámetros opcionales nombre=valor: empieza con ? y se encadenan con & → ?edad=3&nombre=Carlos

El host es subdominio + dominio: le dice a la red a qué máquina ir; el puerto, a qué programa dentro de ella.

Las cuatro partes

Línea inicial

En el request: verbo + ruta + versión.
En la response: versión + código + frase (200 OK).

Headers (cabeceras)

Datos sobre el mensaje, uno por línea: Nombre: valor. Formato, tamaño, credenciales…

Línea vacía

Obligatoria. Marca dónde terminan los headers y empieza el body.

Body (cuerpo)

Los datos en sí: JSON, HTML, una imagen… Es opcional; Content-Type dice su formato.

Estructura de un Request

  • Verbo — qué operación se pide: GET, POST, PUT, DELETE…
  • URI — la ruta al recurso referenciado
  • Versión HTTP — por ejemplo HTTP/1.1
  • Headers — metadatos como pares clave-valor: tipo de cliente, formato del body, caché…
  • Body (opcional) — el contenido del mensaje
POST /Person/ HTTP/1.1
Host: api.miservicio.com
Content-Type: application/json
Content-Length: 123

{
  "Person": {
    "Id": 1,
    "Nombre": "Pablo Páramo",
    "Email": "pparamo@gmail.com",
    "Pais": "Argentina"
  }
}

Un POST completo: verbo + URI + versión, headers, y el body en JSON.

Los verbos HTTP

VerboPara qué se usa¿Datos visibles en la URL?
GETSolicitar un recurso — el más comúnSí, en la URL y el query string
POSTEnviar datos para crear — típico de formulariosNo, viajan en el body
PUTReemplazar el recurso completo (también puede crearlo)No, viajan en el body
PATCHModificar una parte del recursoNo, viajan en el body
DELETEEliminar el recurso identificado en la URI—
HEADComo GET pero sin el contenido: solo headers y código—
La gracia de REST: el verbo dice qué hacés, la URI dice sobre qué. DELETE /productos/5 se lee solo.

Estructura de un Response

  • Status code — cómo le fue al servidor con lo pedido
  • Versión HTTP
  • Headers — metadatos de la respuesta: tipo y largo del contenido, servidor, fecha…
  • Body (opcional) — la representación del recurso solicitado
HTTP/1.1 200 OK
Date: Wed, 23 Oct 2019 19:51:41 GMT
Server: Apache/2.4.29
Content-Type: application/json; charset=UTF-8

[
  { "Id": 1, "Nombre": "Teclado" },
  { "Id": 2, "Nombre": "Mouse" }
]

Los nombres de los headers no distinguen mayúsculas. Una aplicación puede inventar los suyos: por costumbre suelen empezar con X-, como X-Api-Key.

Informativas (100–199) y redirecciones (300–399)

2xx

4xx

Errores del cliente: pediste mal o algo que no existe

5xx
