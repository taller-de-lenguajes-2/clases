Hoy — un mismo mensaje, muchas formas

Ya sabemos armar clases y asociarlas (es parte de, tiene un). Hoy aparece la tercera relación: es un.

Herencia

  • Es el mecanismo por el cual una clase se construye a partir de otra ya existente: la clase nueva obtiene todos los miembros (atributos y métodos) de la clase base, y puede extenderlos o especializarlos
  • Es la relación “es un”: un Auto es un Vehículo · una Vaca es un Animal
  • Lo común se escribe una sola vez en la base; cada derivada agrega solo su diferencia

Beneficio 1 · Reutilización

El código de la clase base se aprovecha en todas sus derivadas.

Beneficio 2 · Polimorfismo

Podemos tratar a todas las derivadas como si fueran la base — lo vemos en unos minutos.

Clases padre, clases hijas

  • Clase padre — también llamada clase base o superclase
  • Clases hijas — también llamadas subclases o clases derivadas
  • En UML la herencia se dibuja con una flecha de triángulo vacío apuntando a la base
Ya conocés los rombos ◆ y ◇ del Tema 02 — el triángulo completa el vocabulario de relaciones.

Un ejemplo: un editor gráfico

Pensemos un sistema de edición de contenidos gráficos — PowerPoint, CorelDraw, Illustrator. Todo lo que se dibuja comparte algo: tiene posición y se puede dibujar.

Herencia en C#

Se declara con el operador : — de la clase derivada hacia la base:

class ClaseDerivada : ClaseBase
{
    // miembros propios de la derivada
}
  • Texto : ObjetoVisual se lee “Texto es un ObjetoVisual”
  • base() invoca al constructor de la clase base
  • La derivada usa X e Y sin volver a declararlos
public class ObjetoVisual   // clase base
{
    public int X { get; set; }
    public int Y { get; set; }
}

public class Texto : ObjetoVisual
{
    public Texto() : base() { … }
}

public class Imagen : ObjetoVisual
{
    public Imagen() : base() { … }
}

Texto titulo = new Texto();
titulo.X = 10;  // heredado de ObjetoVisual

Polimorfismo

Del griego: “con muchas formas”. Es la capacidad de que un mismo mensaje se resuelva de forma distinta según el objeto que lo recibe — y se decide en tiempo de ejecución. Tiene dos caras:

1 · Tratar a la derivada como base

Un objeto de una clase derivada puede usarse donde se espera la base: en parámetros, colecciones, variables.

ObjetoVisual o = new Texto();

2 · virtual / override

La base define métodos virtual con un comportamiento por defecto; cada derivada puede sobreescribirlos con override.

Igual firma, implementación propia.

No confundir con la sobrecarga (Tema 01): allá el compilador elige entre firmas distintas; acá se elige en ejecución entre implementaciones de la misma firma.

Polimorfismo en acción

public class ObjetoVisual
{
    public virtual void Dibujar()
    { Console.WriteLine("dibujo genérico"); }
}

public class Texto : ObjetoVisual
{
    public override void Dibujar()
    { Console.WriteLine("muestro texto"); }
}

public class Imagen : ObjetoVisual
{
    public override void Dibujar()
    { Console.WriteLine("muestro imagen"); }
}

La magia aparece al recorrer la colección — el editor no pregunta qué es cada cosa, solo le pide a cada objeto que se dibuje:

List<ObjetoVisual> diapositiva = new()
{
    new Texto(),
    new Imagen(),
    new Texto()
};

foreach (ObjetoVisual o in diapositiva)
    o.Dibujar();

// muestro texto
// muestro imagen
// muestro texto

Problemas de abstracciones: Liskov

Heredar es fácil; heredar bien es diseño. El principio de sustitución de Liskov (Barbara Liskov, 1987) dice:

“Los objetos de una clase base deben poder reemplazarse por objetos de sus subclases sin alterar el correcto funcionamiento del programa.”
  • La derivada debe cumplir el contrato que promete la base — no vale mentir
  • Si en algún lugar se espera un Pato, cualquier subclase de Pato tiene que servir ahí sin sorpresas
  • Cuando una subclase necesita “anular” comportamiento de la base (no vuelo, no aplica, tiro excepción), la jerarquía está mal planteada

El pato de juguete

public class Pato
{
    public virtual void Quack() { … }
    public virtual void Volar() { … }
}

public class PatoBali : Pato      // ✓ ok
{
    public override void Quack() { Console.WriteLine("¡Quack!"); }
    public override void Volar() { Console.WriteLine("Volando"); }
}

public class PatoJuguete : Pato   // ⚠
{
    public override void Quack() { Console.WriteLine("¡Squeak!"); }
    public override void Volar() { Console.WriteLine("NO VUELO"); }
    public void CargarPilas() { … }
}

El pato de juguete parece un pato… pero como subclase rompe el contrato:

Pato patito = new PatoJuguete();

patito.Volar();
// "NO VUELO" — miente: prometía volar

patito.CargarPilas();
// ✗ no compila: Pato no tiene
//   CargarPilas()
Tratado como Pato, el juguete no cumple lo prometido y no puedo usar lo que le es propio. Viola Liskov por los dos lados.

La salida: abstracciones que encajen

  • La clave es crear abstracciones que se ajusten de manera natural a la lógica del problema
  • A veces conviene tener jerarquías separadas en lugar de forzar una única
  • El pato de goma encaja mejor como Juguete que como Pato
¿Y si un objeto necesita comportamientos de varios orígenes a la vez? Eso lo resuelven las interfaces — próximo tema.
public class Juguete
{
    public virtual void Sonido() { }
    public virtual void Flotar() { }
    public virtual void CargarPilas() { }
}

public class PatoDeGoma : Juguete  // ✓
{
    public override void Sonido()
    { Console.WriteLine("¡Squeak squeak!"); }

    public override void Flotar()
    { Console.WriteLine("Flotando"); }
}
