Los principios SOLID

Cinco pautas de diseño orientado a objetos para escribir código fácil de mantener y de hacer crecer. Las reunió Robert C. Martin.

PrincipioEn una línea
SResponsabilidad única (SRP)Una clase, una sola razón para cambiar. Hoy.
OAbierto/cerrado (OCP)Agregar comportamiento sin modificar lo que ya anda
LSustitución de Liskov (LSP)Una clase hija tiene que poder usarse donde se espera la madre (tema 03)
ISegregación de interfaces (ISP)Interfaces chicas, que nadie tenga que implementar lo que no usa
DInversión de dependencias (DIP)Depender de abstracciones (interfaces), no de clases concretas. Tema 14

Responsabilidad única

«Cada módulo de software debe tener una, y solo una, razón para cambiar.»

Robert C. Martin (traducción libre)

La navaja suiza

Sierra, cuchillo, tijera y tirabuzón en una sola pieza. Si se rompe la bisagra, te quedás sin todas. Para afilar el cuchillo, desarmás todo.

Herramientas separadas

Cada una hace una cosa. Se cambia, se arregla o se mejora sin tocar a las otras.

Una clase con muchas responsabilidades es más difícil de entender, de modificar y de probar.

Un bar con clases

Cada parte tiene una responsabilidad y se comunica con las demás pasándose el pedido.

El mozo no sabe dónde se guardan los ingredientes. El cocinero no sabe qué mesa pidió. Si cambia el proveedor, solo se entera la cocina.

¿Cuántas razones tiene para cambiar?

Volvamos a AccesoDatos. Cada fila es un motivo distinto para abrir la misma clase:

Si cambia…hay que tocar AccesoDatos
la tabla Paciente (una columna nueva)✔
la consulta de turnos (un JOIN más)✔
los médicos pasan a venir de un servicio web✔
la base pasa de SQLite a SQL Server✔
Cuatro razones, una clase. La solución: una clase por entidad, que se encargue solo de guardar y traer esa entidad.

¿Qué es un repositorio?

La responsabilidad única aplicada a los datos: una clase que encapsula todas las operaciones de acceso a datos de una entidad.

Separa

La lógica del negocio («no se repite un DNI») del acceso a los datos (el SQL).

Esconde

De afuera se ve Listar() u Obtener(id). Conexiones, comandos y lectores quedan adentro.

Permite cambiar

De SQLite a SQL Server, a un JSON o a un servicio web, sin tocar el resto del programa.

Sirve para cualquier fuente de datos externa: bases de datos, archivos JSON, servicios web, documentos…

Entre la lógica y los datos

Del lado izquierdo viajan objetos (Paciente). Del lado derecho, SQL y filas. Nadie más ve el SQL.

Un repositorio por entidad

Repositorios/
├── PacienteRepository.cs   ← tabla Paciente
├── MedicoRepository.cs     ← tabla Medico
└── TurnoRepository.cs      ← tabla Turno (con JOIN)

Son las operaciones CRUD (crear, leer, actualizar, borrar). Se suman las búsquedas que haga falta: Buscar(texto), TurnosDelDia(fecha)…

PacienteRepository

public class PacienteRepository(string cadenaConexion)
{
    public Paciente? Obtener(int id)
    {
        using var conexion = new SqliteConnection(cadenaConexion);
        conexion.Open();

        var sql = "SELECT Id, Nombre, DNI, Telefono FROM Paciente WHERE Id = @id";
        using var comando = new SqliteCommand(sql, conexion);
        comando.Parameters.AddWithValue("@id", id);

        using var lector = comando.ExecuteReader();
        return lector.Read() ? LeerPaciente(lector) : null;
    }

    public List<Paciente> Listar()             { … }
    public int Insertar(Paciente paciente)    { … }
    public bool Actualizar(Paciente paciente) { … }
    public bool Eliminar(int id)             { … }

    private static Paciente LeerPaciente(SqliteDataReader lector) { … }
}
  • Es el ADO.NET del tema 08, ordenado
  • Recibe la cadena de conexión: no la inventa
  • Devuelve objetos, nunca un SqliteDataReader
  • Lo que es detalle (LeerPaciente) es private: ocultamiento (tema 01)

Quien lo usa no ve SQL

En una Web API (tema 08)

[HttpGet("{id}")]
public IActionResult Obtener(int id)
{
    Paciente? paciente = repositorio.Obtener(id);
    return paciente is null ? NotFound() : Ok(paciente);
}

En la lógica de la recepción

public int? DarDeAlta(Paciente nuevo)
{
    bool repetido = pacientes.Listar()
        .Any(p => p.DNI == nuevo.DNI);
    if (repetido) return null;

    return pacientes.Insertar(nuevo);
}
El controlador decide qué responder; la recepción decide las reglas; el repositorio solo guarda y trae. Cada uno con su responsabilidad.

El contrato: una interfaz

public interface IPacienteRepository
{
    List<Paciente> Listar();
    Paciente? Obtener(int id);
    List<Paciente> Buscar(string texto);
    int Insertar(Paciente paciente);
    bool Actualizar(Paciente paciente);
    bool Eliminar(int id);
}
  • Dice qué se puede hacer con los pacientes guardados
  • No dice cómo ni dónde
  • Es una interfaz como las del tema 04

Ojo con las versiones que circulan por internet: IEnumerable sin tipo (mejor List<Paciente> o IEnumerable<Paciente>), o Delete(User) en una clase y Delete(int) en la otra. La interfaz y la clase tienen que coincidir.

Dos implementaciones, un contrato

En SQLite

public class PacienteRepository(string cadena)
    : IPacienteRepository
{
    public Paciente? Obtener(int id)
    {
        // SqliteConnection, SELECT … WHERE Id = @id
    }
    …
}

En un archivo JSON

public class PacienteRepositoryJson(string archivo)
    : IPacienteRepository
{
    public Paciente? Obtener(int id)
        => Leer().FirstOrDefault(p => p.Id == id);
    …
    private List<Paciente> Leer() => JsonSerializer
        .Deserialize<List<Paciente>>(File.ReadAllText(archivo));
}

Por dentro no se parecen en nada. Por fuera son iguales: los dos son un IPacienteRepository.

La única línea que cambia

// Program.cs: el único lugar que sabe dónde están los datos
IPacienteRepository repositorio = usarJson
    ? new PacienteRepositoryJson("pacientes.json")
    : new PacienteRepository("Data Source=clinica.db");

var recepcion = new Recepcion(repositorio);    // Recepcion recibe un IPacienteRepository
recepcion.DarDeAlta(new Paciente { Nombre = "Lucía Fernández", DNI = "42000111" });

dotnet run

Repositorio: PacienteRepository
Alta de Lucía Fernández con Id 6.

dotnet run -- json

Repositorio: PacienteRepositoryJson
Alta de Lucía Fernández con Id 1.
Recepcion no cambió ni una línea. Que reciba el repositorio en el constructor, en vez de crearlo, es la idea de la inyección de dependencias (tema 14).

Arquitectura en capas

  • Cada capa usa solo a la de abajo
  • Ninguna se saltea una capa: el controlador no abre conexiones
  • En proyectos chicos, la capa de servicios puede no estar: el controlador usa al repositorio directo, como en la Web API del tema 08
Es separar responsabilidades a escala de todo el sistema. En el tema 10 lo vemos con MVC.

Qué va en un repositorio y qué no

Sí

  • El SQL, siempre con parámetros
  • Abrir y cerrar conexiones
  • Pasar de filas a objetos, y de objetos a parámetros
  • Devolver null o false si no existe

No

  • Console.WriteLine o HTML: no muestra nada
  • Reglas del negocio («un médico atiende hasta 20 turnos por día»)
  • Devolver un SqliteDataReader o un DataTable
  • SQL de otra entidad

La prueba: ¿podría cambiar de SQLite a JSON sin tocar nada fuera del repositorio? Si la respuesta es no, algo se escapó.
