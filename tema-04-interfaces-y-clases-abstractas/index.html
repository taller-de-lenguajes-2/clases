Interfaces y clases abstractas

Contratos que las clases se comprometen a cumplir

El problema que traemos

  • El pato de juguete no encajaba en la jerarquía de Pato: mentía al volar y escondía CargarPilas()
  • En el ejercicio de vehículos, ninguna clase base única evitaba que alguien mintiera: la bicicleta no tiene motor, el auto no vuela
  • La herencia simple obliga a elegir una sola familia — y la realidad a veces necesita capacidades combinadas
Hoy sumamos dos herramientas: la clase abstracta (una base que no se puede instanciar) y la interfaz (un contrato puro que se puede combinar).

Clase abstracta

  • Es una clase pensada solo para ser heredada: no se pueden crear instancias de ella
  • Representa un concepto incompleto o genérico — existe una figura, pero nadie dibuja “una figura”: dibuja un cuadrado o un círculo
  • Se declara con el modificador abstract
public abstract class FiguraGeometrica
{ … }

var f = new FiguraGeometrica();
// ✗ no compila: es abstracta

Reglas del juego

  • Sus métodos abstract no tienen implementación: solo la firma
  • Si una clase tiene al menos un método abstracto, la clase debe ser abstracta
  • Puede mezclar métodos abstractos con métodos y atributos comunes
  • Las derivadas deben implementar (con override) todo lo abstracto — o ser abstractas también

Ejemplo: FiguraGeometrica

public abstract class FiguraGeometrica
{
    // contrato: toda figura sabe esto
    public abstract double Area();
    public abstract double Perimetro();
}

public class Cuadrado : FiguraGeometrica
{
    private double lado;

    public Cuadrado(double lado)
    { this.lado = lado; }

    public override double Area() { return lado * lado; }
    public override double Perimetro() { return lado * 4; }
}
public class Rectangulo : FiguraGeometrica
{
    private double b, h;

    public Rectangulo(double b, double h)
    { this.b = b; this.h = h; }

    public override double Area() { return b * h; }
    public override double Perimetro() { return 2 * (b + h); }
}
  • La base declara el contrato; cada derivada lo implementa con override
  • Sin implementar Area() y Perimetro(), Cuadrado no compila

Abstractas + polimorfismo

No puedo instanciar FiguraGeometrica… pero sí puedo usarla como tipo. El polimorfismo del Tema 03 funciona igual:

  • Una lista de figuras sin saber cuál es cuál
  • Cada una calcula su área como le corresponde
  • Y acá nadie miente: el contrato obliga a que toda figura tenga área y perímetro
List<FiguraGeometrica> figuras = new()
{
    new Cuadrado(3),
    new Rectangulo(3, 5)
};

double total = 0;
foreach (FiguraGeometrica f in figuras)
    total += f.Area();

Console.WriteLine(total);  // 9 + 15 = 24

La interfaz

  • En teoría de objetos, la interfaz de una clase es todo lo que podemos hacer con ella: sus métodos y propiedades públicas
  • En C#, una interface lleva esa idea al extremo: es un contrato puro — solo firmas, sin implementación ni estado
  • La clase que la implementa se compromete a cumplir cada miembro del contrato
public interface IPrinter
{
    // solo la firma: qué, no cómo
    void Imprimir(Documento doc);
}
  • Puede declarar métodos, propiedades, indexadores y eventos
  • Por convención, el nombre empieza con I: IPrinter, IVolador
  • Una clase puede implementar varias interfaces a la vez — a diferencia de la herencia, que es de una sola base

Un contrato, muchas implementaciones

public class Impresora : IPrinter
{
    public void Imprimir(Documento doc)
    {
        // lo manda al hardware
    }
}

public class Consola : IPrinter
{
    public void Imprimir(Documento doc)
    {
        Console.WriteLine(doc.ToString());
    }
}

Quien necesita imprimir no conoce ni le importa la implementación:

IPrinter salida = new Consola();
salida.Imprimir(doc);

salida = new Impresora();
salida.Imprimir(doc);  // mismo código
El contrato garantiza que cualquier IPrinter sabe imprimir. Polimorfismo, otra vez — ahora sin compartir ni una línea de código entre las clases.

Los patos, resueltos

El pato y el pato de goma comparten algunos comportamientos, pero no todos. En vez de forzar una jerarquía, separamos las capacidades en interfaces:

  • Pato hace sonidos y vuela
  • PatoDeGoma solo hace sonidos — y ya no miente: nunca prometió volar
Las interfaces permiten sumar comportamiento de varios orígenes a una misma clase: la “herencia múltiple” que las clases no tienen.
public interface IEmisorSonido { void Sonido(); }

public interface IVolador { void Volar(); }

public class Pato : IEmisorSonido, IVolador
{
    public void Sonido() { Console.WriteLine("¡Quack!"); }
    public void Volar()  { Console.WriteLine("Volando"); }
}

public class PatoDeGoma : IEmisorSonido
{
    public void Sonido() { Console.WriteLine("¡Squeak!"); }
}

¿Abstracta o interfaz?

Clase abstractaInterfaz
¿Se puede instanciar?✗✗
¿Puede tener campos / estado?✓✗
¿Puede traer implementación?✓ métodos concretos y abstractos✗ solo firmas (default methods desde C# 8, no los usamos)
¿Constructor?✓✗
¿Cuántas por clase?una sola basetodas las que necesites
La relación se lee…“es un” con código común“sabe hacer” / “es capaz de”
Regla práctica: si hay código y estado para compartir entre parientes → clase abstracta. Si es una capacidad que pueden tener clases sin parentesco → interfaz. Y se combinan: una clase abstracta puede implementar interfaces.

Interfaces chicas y específicas

Anticipo de un principio de diseño (ISP — Interface Segregation Principle): nadie debería verse obligado a depender de métodos que no usa.

✗ Una interfaz gigante

public interface IVehiculo
{
    void EncenderMotor();
    void Conducir();
    void Volar();
}

La bicicleta queda obligada a “implementar” un motor que no tiene — el pato de juguete, otra vez.

✓ Varias específicas

public interface IConMotor
{
    void EncenderMotor();
    void ApagarMotor();
}
public interface IConducible { void Conducir(); }

public interface IVolador { void Volar(); }

Cada clase toma solo los contratos que puede cumplir.

Los vehículos, resueltos

public class Avion : IConMotor, IConducible, IVolador
{
    public void EncenderMotor() { … }  public void ApagarMotor() { … }
    public void Conducir() { … }       public void Volar() { … }
}

public class Auto : IConMotor, IConducible
{
    public void EncenderMotor() { … }  public void ApagarMotor() { … }
    public void Conducir() { … }
}

public class Bicicleta : IConducible
{
    public void Conducir() { … }
}

Cada vehículo implementa exactamente lo que puede hacer — nadie miente, nadie esconde métodos:

// todo lo que vuela, a volar:
List<IVolador> escuadron = new()
{ new Avion() };

// todo lo conducible, a la ruta:
List<IConducible> caravana = new()
{ new Avion(), new Auto(),
  new Bicicleta() };
Liskov contento: donde se espera un IVolador solo entran cosas que de verdad vuelan.

Para pensar: ¿y si Avión y Auto comparten código del motor? Pista: abstracta + interfaces se combinan.
